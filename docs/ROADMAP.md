# 路线图变更制度

本文档只管理“路线图如何变化”。当前版本的详细功能、承接关系和验收门以根目录 [README.md](../README.md#7-重新设计后的版本路线图) 为准；已经发布的结果以 [CHANGELOG.md](../CHANGELOG.md) 和 Git 标签为准。

## 1. 三类事实

路线图、发行历史和代码状态是三类不同事实：

| 事实 | 权威来源 | 是否可以回改 |
|---|---|---|
| 未来计划 | README 路线图 | 可以，但必须记录原因和影响 |
| 已发布能力 | CHANGELOG + `vX.Y.Z` Git 标签 | 不可改写，只能用新版本修正 |
| 当前实现 | 对应 Git 提交、测试和 ReleaseBundle | 通过 GitFlow 演进 |

路线图版本是沟通用的里程碑，Git 标签才是实际发行身份。正式标签统一使用三段式语义化版本，例如 `v0.13.0`；README 可继续使用便于阅读的 `V0.13`。

## 2. 版本状态

每个正在执行或即将执行的版本使用以下一种状态：

- **Planned：** 方向已列入路线图，范围仍可调整。
- **Ready：** 前置依赖、交付物和验收门已经清楚，可以开始开发。
- **In Progress：** 已有对应分支或任务正在实现。
- **Frozen：** 候选范围冻结，只接受达到验收门所需的修复。
- **Released：** 已合并到 `main`、创建标签并写入 CHANGELOG。
- **Cancelled：** 不再实现；保留记录和原因，不伪装成从未存在。

## 3. 插入版本

### 后续版本尚未发布

允许插入并顺延仍处于 Planned/Ready 的版本。一次插入必须同时完成：

1. 写明缺失能力为何不能并入相邻版本。
2. 定义新版本承接的产物、交付物和验收门。
3. 更新所有后续版本的编号、前置依赖和文内引用。
4. 检查 Schema、存档、媒体、UI、AI 回退和测试是否受到影响。
5. 在本文的“路线图变更记录”追加一条记录。

完成标准：README 中不存在重复编号、悬空承接或引用旧编号的后续版本。

### 相邻版本已经发布

已发布历史保持不变，缺失能力进入新的后续版本。不能把一个新版本插入已经发生的 Git 历史，也不能重新使用已经发布的版本号。

例如 `v0.14.0` 已发布后才发现缺少一项前置能力，应把它安排到 `v0.15.0` 或更晚版本，而不是重新定义 `v0.14.0`。

## 4. 修改现有版本

| 当前状态 | 允许的修改 | 必须采取的动作 |
|---|---|---|
| Planned | 调整、拆分、合并、重排 | 更新承接关系、验收门和变更记录 |
| Ready | 澄清范围或拆分版本 | 重新确认依赖和 Ready 条件 |
| In Progress | 小范围澄清；重大变化优先拆到后续版本 | 更新任务、测试、兼容性和 PR 说明 |
| Frozen | 只修复阻断验收的问题 | 其余变化进入下一版本 |
| Released | 不修改版本含义 | 创建补丁版或新的功能版本 |

如果一次修改同时影响两个以上核心产物，或改变存档/Schema/ReleaseBundle 的兼容含义，应增加一份架构决策记录，而不是只改一句路线图。

## 5. 版本号选择

- `v0.14.1`：对 `v0.14.0` 的兼容修复，不承担新的路线图里程碑。
- `v0.15.0`：新增能力或改变未稳定的内部接口。
- `v1.0.0`：达到首次正式发布承诺。
- `v0.15.0-alpha.1`：内部或小范围验证包。
- `v0.15.0-beta.1`：功能已完整、重点验证兼容和稳定性的测试包。
- `v0.15.0-rc.1`：预期可成为正式版的候选包。

同一个版本号只能对应一个不可变发布结果。重新构建必须产生相同内容；内容发生变化就使用新版本号。

## 6. 变更检查清单

修改路线图的 PR 必须回答：

- 这次变化解决什么缺口？
- 哪些版本号、承接关系和验收门受影响？
- 是否改变 StoryPack、存档、媒体或 ReleaseBundle 兼容性？
- 是否增加新的 Player、Creator Studio 或 Developer UI 状态？
- 联网或 AI 能力是否有确定性的离线回退？
- 测试、迁移、隐私、安全、成本和资产权利是否需要新增要求？
